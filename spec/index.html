SPARQL Examples is a standard to collect curated, runnable "question → SPARQL query" pairs for [[SPARQL]] endpoints, stored as RDF so that the examples themselves can be queried, tested, and compiled into several downstream artifacts (raw .rq files, JSON-LD, a graph loadable into an endpoint's own .well-known/sparql-examples, and a documentation website). This document specifies the RDF vocabulary, file and directory conventions, and conformance checks that a collection following this model is expected to satisfy. It reuses terms from the SHACL SPARQL-based constraints vocabulary [[SHACL-AF]] together with a small extension ontology, https://purl.expasy.org/sparql-examples/ontology#, and documents the checks that the [[SPARQL-EXAMPLES-UTILS]] tooling runs against a collection.

If building your own collection on github start with [[SPARQL-EXAMPLES-TEMPLATE]], that will setup actions and code that will help you maintain your collections.

This is not a W3C document and has no standing in the W3C process. It is an informal specification maintained by the SIB Swiss Institute of Bioinformatics, written to make explicit and reviewable the conventions that the sparql-examples-utils tooling already enforces against the sib-swiss/sparql-examples repository and the collections created from the [[SPARQL-EXAMPLES-TEMPLATE]]. It describes existing, deployed practice rather than proposing new design. Please file issues or pull requests against the GitHub repository if this document and the tooling disagree — the tooling's SHACL shape (§ 7.1) is the normative source of truth for the per-example constraints.

Introduction

Public SPARQL endpoints in bioinformatics are numerous, each with its own schema, and the [[SPARQL]] query language itself has a learning curve. SPARQL Examples addresses this by collecting real question/query pairs contributed by people who know a given endpoint well, one query per file, as small RDF descriptions rather than as bare .rq text files. Storing an example as RDF alongside its own metadata (a human-readable explanation, the endpoint it targets, optional keywords) makes the collection itself queryable, lets a single toolchain validate every example the same way regardless of which project it belongs to, and lets that toolchain compile the same source data into multiple consumer-facing formats. See [[SPARQL-EXAMPLES-GIGASCIENCE]] for the methodology and motivating use cases in more detail.

This document specifies:

  • the directory layout a collection uses (§ 2);
  • the RDF vocabulary used to describe one example (§ 3);
  • a complete worked example (§ 4);
  • the convention for rich-text comments (§ 5);
  • prefix declarations shared across queries (§ 6);
  • the conformance checks a collection is validated against (§ 7);
  • the artifacts the tooling compiles a collection into (§ 8).

It is deliberately not a tutorial for contributing an example (see the sparql-examples README and the [[SPARQL-EXAMPLES-TEMPLATE]] for that) and not a command-line reference for [[SPARQL-EXAMPLES-UTILS]] (see that repository's own documentation).

Repository layout

A conforming collection is a directory tree of the shape: 

examples/
  prefixes.ttl              # prefixes shared by every project
  <Project>/
    prefixes.ttl             # OPTIONAL, project-specific prefixes
    <name>.ttl               # one example
    <name>.ttl
    ...
  <Project>/
    ...
  • Each immediate subdirectory of examples/ is a project: a set of examples that target the same SPARQL endpoint or closely related endpoints (for instance examples/UniProt/ or examples/Rhea/).
  • Every other .ttl file directly inside a project directory is an example: one file describing one SPARQL executable (§ 3). The file's base name is not otherwise constrained by this specification — short numeric names (9.ttl) and short mnemonic names (125_CORDIS_EURIO_cited_project_results_in_uniprot.ttl) are both in use across the collection, and the base name is not required to equal the example resource's IRI local name, although in practice it usually does.
  • A file literally named prefixes.ttl is never treated as an example, at either the examples/ root (prefixes shared by every project) or inside a project directory (prefixes specific to that project, additive to the shared ones). A project directory is not required to have its own prefixes.ttl.

An example file MUST describe exactly one SPARQL executable resource. Nothing in the RDF data model itself prevents more than one per file, but the tooling's per-file reporting (test results, one generated documentation page per example, the file name shown in the generated website) assumes a 1:1 mapping between file and example, so collections SHOULD NOT rely on more than one executable per file being supported.

The example vocabulary

An example reuses classes and properties from the SPARQL-based constraints part of SHACL [[SHACL-AF]] (namespace prefix sh:, http://www.w3.org/ns/shacl#) — which already defines a vocabulary for "a SPARQL query together with its own prefix declarations" for the purposes of SHACL rules and constraints, and turns out to be exactly the shape needed here too — together with a small extension ontology, prefix spex:, https://purl.expasy.org/sparql-examples/ontology#, that adds what SHACL does not have: a DESCRIBE-query class and a federation annotation.

A small number of additional, optional metadata properties are recognised by the generated documentation but are not required and are rarely populated in practice: dcterms:contributor (who contributed the example), dcterms:license (a license other than the collection's default), dcterms:isPartOf (a page the query was taken from), and cito:usesMethodIn (CiTO, a citation to a paper describing the method the query implements).

Finally, when a collection is compiled (§ 8) the tooling additionally asserts, for each example resource, provenance triples that authors do not and should not write by hand: spex:file_name and spex:file_path (the source file), and spex:project (the containing project's directory name); a project's own resource additionally gets spex:sub_project when one project nests another.

A complete example

The following retrieves human enzymes that metabolize sphingolipids from the UniProt SPARQL endpoint, federating with the Rhea endpoint for the reaction chemistry: 

@prefix ex: <https://sparql.uniprot.org/.well-known/sparql-examples/> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix schema: <https://schema.org/> .
@prefix sh: <http://www.w3.org/ns/shacl#> .
@prefix spex: <https://purl.expasy.org/sparql-examples/ontology#> .

ex:040
    a sh:SPARQLExecutable, sh:SPARQLSelectExecutable ;
    rdfs:comment "Retrieve human enzymes that metabolize sphingolipids and are annotated in ChEMBL"@en ;
    sh:prefixes _:sparql_examples_prefixes ;
    sh:select """PREFIX CHEBI: <http://purl.obolibrary.org/obo/CHEBI_>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
PREFIX rh: <http://rdf.rhea-db.org/>
PREFIX taxon: <http://purl.uniprot.org/taxonomy/>
PREFIX up: <http://purl.uniprot.org/core/>

SELECT DISTINCT ?protein ?chemblEntry WHERE {
  SERVICE <https://sparql.rhea-db.org/sparql> {
    ?rhea rdfs:subClassOf rh:Reaction ;
      rh:side/rh:contains/rh:compound/rh:chebi/rdfs:subClassOf+ CHEBI:26739 .
  }
  ?protein up:annotation/up:catalyticActivity/up:catalyzedReaction ?rhea ;
    up:organism taxon:9606 ;
    rdfs:seeAlso ?chemblEntry .
  ?chemblEntry up:database <http://purl.uniprot.org/database/ChEMBL> .
}""" ;
    schema:keywords "enzyme" ;
    schema:target <https://sparql.uniprot.org/sparql/> ;
    spex:federatesWith <https://sparql.rhea-db.org/sparql> .

Note how spex:federatesWith names exactly the one endpoint reached by the SERVICE clause inside sh:select, while schema:target names the endpoint the query is actually submitted to.

Rich-text comments

rdfs:comment MUST take one of two literal forms:

  1. a plain, language-tagged string (RDF's rdf:langString), for a comment that is ordinary text with no markup, e.g. "Select all Rhea reactions mapped to enzyme classification (EC numbers)"@en; or
  2. a string typed rdf:HTML, when the explanation needs inline markup such as a link or emphasis, e.g. "Retrieve the MNXref metabolite with name <em>N,N-dimethyl-beta-alanine</em>, together with molecular information."^^rdf:HTML.

The value of an rdf:HTML-typed comment MUST be valid HTML markup, not raw Markdown syntax. In other words, a contributor may draft the explanation in GitHub-flavored Markdown, but the literal committed to the .ttl file is the rendered HTML, not the Markdown source: **bold** or [text](url) left unconverted inside an rdf:HTML literal is a defect, not a stylistic choice, since a consumer of the RDF has no reason to expect to have to run a Markdown renderer over a literal already typed as HTML. [[SPARQL-EXAMPLES-UTILS]]'s markdown-html check (§ 7.2) flags common unconverted Markdown patterns (bold, links, inline code, fenced code blocks, headings, list items) found inside an rdf:HTML literal's text content as a warning.

Prefix declarations

A query's own text is free to declare every prefix it uses with ordinary PREFIX lines, as in § 4. Separately, and orthogonally, a collection can maintain a set of reusable prefix declarations using SHACL's own vocabulary for this purpose, so that tooling which needs to resolve a project's prefixes without parsing every query string can do so directly from the RDF: 

prefix sh: <http://www.w3.org/ns/shacl#>
prefix xsd: <http://www.w3.org/2001/XMLSchema#>

_:sparql_examples_prefixes sh:declare _:prefix_up .
_:prefix_up
  sh:prefix "up" ;
  sh:namespace "http://purl.uniprot.org/core/"^^xsd:anyURI .

examples/prefixes.ttl holds declarations shared by every project; a project's own prefixes.ttl, when present, adds declarations specific to that project's namespaces. An example's sh:prefixes triple (§ 4) points at the same blank node identifier, _:sparql_examples_prefixes, used across every prefixes.ttl in scope for it, so that when a project's files are concattenated before being loaded as one file the declarations merge into one set. If the example files have to be fully standalone the prefix sets musts be identified by a stable IRI.

Conformance checks

[[SPARQL-EXAMPLES-UTILS]]'s test command validates a collection against two kinds of check: a SHACL shape that every example resource is validated against directly, and a set of independent checkers that each parse (and, optionally, execute) every query and produce one result per example, classified as pass, warn, or fail. A fail from any checker fails the run; a warn never does — it is instead surfaced for a human to look at without blocking automated validation; every other result is a pass. Every result records which checker, project, file, and (where applicable) which query within the file produced it, and the command can render the full set of results as a Markdown report grouping failed and warned examples by project and file.

The SHACL shape

Every resource in the target class sh:SPARQLExecutable is validated, using RDF4j's SHACL engine, against the following shape. It is the normative statement of the per-example structural constraints; the prose in § 3 summarises it but this shape is authoritative where the two differ. 

PREFIX sh:<http://www.w3.org/ns/shacl#>
PREFIX sd:<http://www.w3.org/ns/sparql-service-description#>
PREFIX schema:<https://schema.org/>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
PREFIX rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
PREFIX spex: <https://purl.expasy.org/sparql-examples/ontology#>
[] sh:targetClass sh:SPARQLExecutable ;
	sh:property [
		sh:path [ sh:alternativePath ( sh:select sh:ask spex:describe sh:construct ) ] ;
		sh:maxCount 1 ;
		sh:minCount 1
	] ,
	[
		sh:path rdfs:comment ;
		sh:minCount 1 ;
		sh:or ( [
				sh:datatype rdf:langString ;
			]
			[
				sh:datatype rdf:HTML ;
			] )
	], [
	sh:path schema:target;
		sh:minCount 1 ] , [
	sh:path schema:keyword;  # Typo not allowed
		sh:maxCount 0 ] , [
	sh:path schema:keyowrds; # Typo not allowed
		sh:maxCount 0 ] , [
	sh:path schema:keywords; # Encouraged but not required.
		sh:minCount 0 ;
        # Ending with a whitespace is probably an typo
		sh:pattern "^[^\s].*[^\s]$" ] , [
    sh:path spex:federatesWith;
        sh:minCount 0 ] .

In prose, this requires that every example: has exactly one query (across sh:select/sh:ask/spex:describe/sh:construct); has at least one rdfs:comment, typed as either a language-tagged string or rdf:HTML; has at least one schema:target; never uses the property schema:keyword (singular) or the misspelling schema:keyowrds; and, if schema:keywords is present, does not start or end with whitespace (almost always a typo). spex:federatesWith is unconstrained by the shape itself (sh:minCount 0) — its consistency with the query text is instead checked dynamically, below.

Checkers

The checkers currently implemented:

cartesian-joinyes (warning only) The query's algebra does not contain a group of triple patterns disconnected from the rest of a join scope, which would force the query engine to evaluate a cartesian product.

Generated artifacts

A collection following this specification is a build input, not the final product consumers use. [[SPARQL-EXAMPLES-UTILS]]'s convert command compiles it into:

  • a single merged Turtle or JSON-LD file per project (or for the whole collection), including the provenance triples from § 3, suitable for loading into the target endpoint itself, conventionally in a named graph at <endpoint>/.well-known/sparql-examples;
  • one .rq file per example, following the naming convention used by grlc so a collection can be exposed as a set of Linked Data APIs without further transformation;
  • one Markdown page per example plus an index, each with a Mermaid diagram of the query's algebra, used to build the documentation website this specification is itself published alongside; and
  • the test report described in § 7.

Because every example carries its own schema:target, the merged graph can also be queried directly to answer questions about the collection itself, for instance to find every example that targets more than one distinct endpoint: 

PREFIX sh: <http://www.w3.org/ns/shacl#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
PREFIX spex: <https://purl.expasy.org/sparql-examples/ontology#>

SELECT DISTINCT ?sq ?comment ?query
WHERE {
    ?sq a sh:SPARQLExecutable ;
        rdfs:comment ?comment ;
        sh:select|sh:ask|sh:construct|spex:describe ?query .
} ORDER BY ?sq
